# Agents (MCP server)

- This folder serves MCP over streamable HTTP (`rmcp` behind `axum`) at `http://127.0.0.1:<port>/mcp`, off until turned on in the Agents tab or Settings > Agents. It binds to 127.0.0.1, accepts only loopback `Host` headers and refuses any request with an `Origin` header. No token.
- `AgentHost` (managed as `Arc<AgentHost>`) owns the server, agent sessions, pending approvals and history. It reaches the window through the `Notifier` trait, so tests run it without Tauri. Server settings and the global switches (`allowRawSql`, `allowChanges`, history, `queryTimeoutSecs` for reads, 60 by default) live in `agent.json`, owned by Rust.
- Access is per connection: `ConnectionProfile.agentAccess` with mode `off` (default), `readOnly` or `ask`, and an optional database list. Where a session is bound to one database (`DatabaseSession::catalog`, Postgres and D1) the list names those databases, elsewhere the ones tools take. Every call re-reads the profile, and saving or deleting a connection closes its agent sessions.
- Agents call `open_session` first and pass its id to every other tool. Agent sessions are their own `DatabaseSession`s, kept apart from the UI's `SessionManager`, with one read-only context per database. They close on `close_session`, from the Agents tab, after 10 minutes idle, when the server is turned off, and on exit.
- Reads run in read-only contexts (`open_context(.., ContextAccess::ReadOnly)`): MySQL sets `SET SESSION TRANSACTION READ ONLY` on every (re)connect, Postgres starts the connection with `default_transaction_read_only=on`, SQLite opens the file read only, and D1 has no such mode. Raw SQL is checked first by `DatabaseSession::classify`, built on each driver's splitter (`classify.rs` per driver, shared tokenizer in `db/classify.rs`). Structured reads are written by `DatabaseSession::read_sql` (`db/read_query.rs` plus each driver's `SqlWriter`), so agents rarely need raw SQL.
- Changes (`ask` mode) build their SQL with the same driver code as the UI (`row_changes_sql`, `table_design_sql`, `object_sql`), then wait in `Approvals` until the user answers in `AgentApprovalModal`. The request carries the call's arguments, and row tools add a `RowPreview` (current values read by key next to the new ones). A new request opens the review once. Closing it leaves the request pending in the Agents tab. No answer in 5 minutes of unlocked time rejects. Approved SQL runs with `execute_batch`.
- The UI is the Agents global tab (`pages/Agents/`), opened from the title bar button: Activity (open sessions, sessions closed that day from history, pending approvals and the day's calls), Access (every connection's `agentAccess`, saved with `save_connection`) and Server (`AgentConfig`). Settings > Agents only has the on switch.
- Every tool call goes through `AgentServer::call_tool`, which hides and refuses tools switched off globally (`tool_enabled`) and writes a `HistoryEntry` with the exact reply. History is a `DayLog` in `agent_history/` under a key stored in the vault (`agent:historyKey`). A vault reset deletes it. With history on and the vault unavailable or locked, the server doesn't start until it can.
- `slow_queries` reads `DatabaseSession::query_history` (the slow queries view's data) with the agent's `order_by`, mean by default, under the same timeout and cancel as reads. Server statistics cover every database, so with a database list set only statements from shared databases are returned, and those naming no database are dropped. Running queries aren't exposed.
- Agents get no SSH tools. `tests.rs` pins the exact tool list, so a new tool has to be added there on purpose.
- Events to the frontend: `agent-status-changed`, `agent-sessions-changed`, `agent-approvals-changed`, `agent-history-added`, read by `states/agentState.ts`.
