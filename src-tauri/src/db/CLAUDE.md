# Database drivers

## Database independence

- Generic code only talks to the `DatabaseSession` trait (`session.rs`). `DriverOptions` (`mod.rs`) is a `kind`/`options` tagged enum, and the `match` arms in that file are the only place that switches on kind (connect, required secrets, statement splitting).
- All MySQL code lives in `mysql/`: options, connect + SSL modes, metadata via `information_schema`, result reading, the statement splitter (quotes, all comment styles, `/*! */`, `DELIMITER`), identifier quoting.
- All Postgres code lives in `postgres/`. It has its own small wire client (`client/`) on `postgres-protocol`, because tokio-postgres drops the column details of text-mode results. User SQL runs one statement at a time with the extended protocol (Parse, Bind, Describe portal, Execute with a row cap, Sync) and text results. The portal's RowDescription gives each column's type OID, table OID and column number. The driver's own catalog queries use the extended protocol with text parameters and text results. Type OIDs resolve through `types.rs` (built-ins inline, the rest cached from `pg_type`), and `relations.rs` maps table OID + column number back to schema, table, column, NOT NULL and primary key. Metadata reads `pg_catalog`, not `information_schema`. `ddl.rs` rebuilds CREATE TABLE from the catalog since Postgres has no SHOW CREATE TABLE. The splitter handles `$tag$` quotes, `E''` strings, nested comments and `BEGIN ATOMIC` bodies. `design.rs` is the Postgres table designer: renames and comments are separate statements, indexes are `CREATE INDEX` / `DROP INDEX` unless they back a constraint, AUTO_INCREMENT maps to an identity column, and existing columns can't be reordered. Expression, partial and exclusion indexes are left out of the design so the designer never touches them.
- All SQLite code lives in `sqlite/`, split into a core and a backend. The core (`session.rs`, `metadata.rs`, `results.rs`, `sqlgen.rs`, `design.rs`, `splitter.rs`) only talks to the `SqliteConnection` and `SqliteConnector` traits in `connection.rs`: run one statement with bound parameters and get columns, rows as `SqlValue`, the change count and the inserted rowid. `local.rs` is the file backend on rusqlite (bundled SQLite, with blocking calls on `spawn_blocking`). Each query tab gets its own connection, so transactions stay per tab. Metadata comes from `sqlite_master` and plain PRAGMA statements (`table_xinfo`, `index_list`, `index_info`, `foreign_key_list`), not the `pragma_*` table functions D1 doesn't document, and `definition.rs` reads generated expressions, collations and AUTOINCREMENT from the stored CREATE TABLE text because no pragma reports them. Result columns get their source table from SQLite's column metadata. When a backend can't report that, `source.rs` reads the table from the statement if it's a plain single-table SELECT whose columns are `*` or bare names (no aliases, since columns are matched by name), so those results stay editable. The tree's top level is `main` plus attached databases. The designer only does what ALTER TABLE can (rename the table, rename/add/drop columns) plus standalone indexes. Anything else is refused with an explanation, because a rebuild drops the old table, and with foreign keys on that fires ON DELETE actions on tables that reference it.
- Cloudflare D1 (`sqlite/d1.rs`) is a second backend for the same core: its own `DriverOptions` variant (`D1Options`: account ID, database name or UUID, an `apiToken` secret slot) and `src/databases/d1/` in the frontend, which spreads the SQLite frontend module. Each statement is one request to the `/raw` endpoint. Parameters must be text, rows come back as JSON (blobs as byte arrays) with column names only, so only plain single-table SELECTs are editable (see `source.rs` above). BEGIN and COMMIT are refused, so `run_batch` sends a `batch` request, which D1 runs as one transaction without saying which statement failed. `_cf_` tables are hidden, `list_catalogs` / `switch_catalog` move between the account's databases (`SqliteConnector::with_catalog`), and `sqlgen` keeps each generated statement under D1's 100 KB limit.
- `DesignOptions.capabilities` tells the designer UI which fields the server has (engine, charset, column collation, ON UPDATE, index prefix lengths, reordering, virtual generated columns), and `indexMethods` fills the index method picker.
- Postgres sessions work in one database, and the tree's top level holds its schemas (`DatabaseModule.namespace`). `list_catalogs` / `switch_catalog` move a session to another database in place, reusing its login and tunnel. Open tabs are saved per database (`catalog`).
- Values cross IPC as text (`Option<String>`) with a `ValueCategory` per column for rendering. Binary is `0x` hex, BIT is decimal.
- Adding a database: a Rust module implementing `DatabaseSession`, a `DriverOptions` variant, a frontend `DatabaseModule`, and the matching TS option types in `src/types/connection.ts`.

## Sessions and contexts

- `open_session` connects and registers an `OpenSession` in `SessionManager`. Metadata calls share one connection per session. Each query tab gets its own connection ("context", `open_query_context`) so session variables and transactions stay per tab. Contexts reconnect after a dropped connection and ping after a minute idle.
- `execute_query` splits the SQL with the kind's splitter, runs statements in order, and stops at the first failure, which is reported on that statement's outcome rather than as a command error. Each outcome goes to the tab over a `Channel` as soon as its statement finishes (drivers implement `execute_streaming`). The command returns how many it sent, because channel messages can arrive after the reply.
- The tab's row limit (`QueryTabState.rowLimit`, starting from the `defaultRowLimit` setting, 0 for none) is enforced on the server, so it plans and stops as it would for a LIMIT. MySQL sets `sql_select_limit` before each run. Postgres and SQLite (both backends) append `LIMIT` to reads whose top level has no LIMIT (or FETCH on Postgres) and don't write (`classify::with_row_limit`), and Postgres also passes the limit as Execute's row cap for statements that can't take one. Each asks for one row more than the limit so the result can say it was cut off.
- Cancel (`cancel_query`) opens a short side connection: MySQL runs `KILL QUERY <id>`, Postgres sends a CancelRequest with the context's key. SQLite interrupts the context's connection in place.

## Generated SQL and DDL

- All SQL that the app writes for the user is generated in the driver (`sqlgen.rs`, `design.rs` in each driver module) and shown in `ReviewSqlModal` before it runs. Its `safety` note says whether a failure rolls back: row changes run in a transaction. DDL does too when `ServerInfo.transactionalDdl` is set (Postgres). Otherwise `ServerInfo.atomicDdl` (set by the driver from the server version) says whether each DDL statement is all or nothing. Literals respect the session's quoting rules (`NO_BACKSLASH_ESCAPES` on MySQL, `standard_conforming_strings` on Postgres), read once at connect into `Dialect`.
- Row changes come in as `RowChange`s to `preview_row_changes`, then `execute_batch` runs them in one transaction on a fresh connection. Rows are matched by primary key, tables without one are read only.
- The table designer edits a `TableDesign`. Every column, index and foreign key carries `originalName` so `alter_sql` can tell renames from drops and adds. FK drops and adds go in their own ALTER statements around the main one. `design.rs` has tests for the diff, extend them when changing it.
- "Copy SQL" templates come from `get_object_sql` / `get_database_sql`. INSERT copies come from `insert_rows_sql` through `get_insert_sql`.

## Slow queries

- `DatabaseSession::activity_support`, `query_history` and `running_queries` (types in `activity.rs`), through `get_query_history` and `get_running_queries`. `SessionInfo.activity` tells the frontend which parts a session has. Each driver keeps its code in its own `activity.rs`. Both run on the metadata connection.
- Every source returns the top `HISTORY_LIMIT` (200) by the `HistoryOrder` the tab is sorted by, and sets `limited` when the server had more. The tab then sorts what it has, and offers a reload when the sort column differs from the one the statements were picked by.
- MySQL reads `performance_schema.events_statements_summary_by_digest` (times in picoseconds, `QUERY_SAMPLE_TEXT` only on MySQL 8+). With performance_schema off (MariaDB's default) it reads `mysql.slow_log` when the slow log goes to a table, and groups entries itself with `normalize`, which replaces literals, collapses value lists and evens out spacing. Running now is `information_schema.PROCESSLIST`, whole seconds on MySQL, `TIME_MS` on MariaDB. The PROCESS check reads `USER_PRIVILEGES`, so a privilege from a role isn't seen.
- Postgres reads `pg_stat_statements` from the schema the extension lives in, with the column names its version has (`*_exec_time` from 1.8), and `stats_reset` from 1.9. A missing extension, a library that wasn't preloaded (SQLSTATE 55000) and a refused view each become a notice. Running now is `pg_stat_activity` without idle sessions. Without `pg_read_all_stats` other logins are hidden, and the notice says so.
- D1 posts the `d1QueriesAdaptiveGroups` GraphQL query `wrangler d1 insights` uses, for the last 24 hours, and needs Account Analytics Read on the token. It has no running now. Local SQLite files have neither.
- When something is off or not allowed, the result carries an `ActivityNotice` with copyable steps (SQL or a config line, and whether it needs a restart). The app never runs them, per the schema rule.
