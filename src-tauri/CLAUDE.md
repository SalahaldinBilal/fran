# Rust backend

## Tests

- `cargo test` covers the statement splitters and classifiers, the SQL generators and the Postgres type mapping. `db/sqlite/session.rs` runs the SQLite driver end to end against a temp file, `agent/tests.rs` drives the MCP server over HTTP with an MCP client, and `ssh/sftp/tests.rs` runs the transfer code against an in-process russh-sftp server that sends names a real server can't (`../evil`, `a/b`).
- `cargo test --features e2e --test e2e` runs the end-to-end tests (`tests/e2e/`) against real servers in Docker, started and removed by the test run. A filter like `-- postgres_17` limits the run. `DOCKER_HOST=tcp://127.0.0.1:2375` points it at dockerd inside WSL, `FRAN_E2E_<SERVER_ID>=host:port:user:password` at an existing server instead of a container.
- `cargo test --features e2e --test e2e -- vpn::` runs own tunnels against the OpenVPN lab from the sibling `openvpn-rust-bindings` repo (`lab/entrypoint.sh`), with `fran-vpn` as the worker. Build it first with `cargo build -p vpn-worker`: the test finds it in its own target folder, or at `FRAN_VPN_WORKER` (only read with the `e2e` feature). `OVPN_LAB_HOST` overrides the server address, which defaults to the WSL machine's IP on Windows.
- `-- vpn::service` with `FRAN_E2E_SERVICE_VPN=1` runs Fran's VPN service as root in the `fran-linux-check` image (`--cap-add NET_ADMIN --device /dev/net/tun`, Docker's socket mounted, `OVPN_LAB_HOST` set): adapter, route and echo, cleanup after stop and after the connection drops, a script option refused, another protocol version refused.
- Linux-only code (`vault/os_auth/linux.rs`) can be checked from Windows in Docker: an image with Rust and Tauri's dev libraries plus `libpam0g-dev`, both repos mounted, `CARGO_TARGET_DIR` on a volume. `pam_accepts_the_right_password_only` is ignored by default and needs a real account in `FRAN_PAM_USER` and `FRAN_PAM_PASSWORD`. PAM is called through its own small FFI there, not a crate, so the build needs no libclang.
- The Postgres container starts with `shared_preload_libraries=pg_stat_statements` for the slow query tests (`tests/e2e/activity.rs`). An external server given through `FRAN_E2E_POSTGRES_17` needs that too, or those tests fail.
- `-- wireguard::` runs own WireGuard tunnels against kernel WireGuard in an Alpine container (needs the host kernel's module, which WSL 2 has), with keys made by the test and an echo server only on the server's tunnel address. It uses the worker path `vpn::trials` sets and `OVPN_LAB_HOST` like the OpenVPN lab.
- `-- ssh::` runs the SSH lab (`tests/e2e/ssh.rs`): two Alpine OpenSSH containers (a jump host and a target only reachable through it) and Postgres on a private Docker network. It covers host keys per hop, PTY, a tunneled Postgres, local and remote forwards, and SFTP transfers.

## Transports

- TCP, Unix socket, Windows named pipe (MySQL only), TCP over SSH. SSH itself is in `src/ssh/CLAUDE.md`.
- mysql_async has named pipes switched off, so on Windows the pipe is relayed through `LocalForward` (`src/forward.rs`), a 127.0.0.1 port that opens the pipe per connection. The SSH tunnel uses the same relay with `direct-tcpip` channels.
- Kubernetes (`src/kube.rs`): `KubeForward` spawns `kubectl port-forward` with the saved context as `--context` (never kubectl's current one), reads the local port from its output and kills it when the session closes. `list_kube_contexts` fills the form's context picker. kubectl handles kubeconfig and auth, so no secret slots.

## Secrets

- `Vault` (`src/vault/`) keeps every secret in `secrets.vault`, encrypted with XChaCha20-Poly1305 (header bytes as AAD). The 32-byte key lives only in the OS keychain (`keyring`, service `com.fran.app`), or with the app lock on, wrapped in `vault.lock`.
- Fran used to be Fran DB (`com.frandb.app`). `legacy::import_old_data` copies the old data folder into a new install's missing one before anything loads, and a copied vault whose key isn't in the keychain yet takes it from the old `com.frandb.app` entry. Only the database client had shipped then, so nothing else is carried over.
- Secret ids are `<owner>:<id>:<slot>` (`SecretOwner`: `connection`, `identity`, `key`, `proxy`, `vpn`). VPN profiles keep `vpn:<id>:private` (client key, written only by import and `set_vpn_key`, or for WireGuard the private key, written by import, `set_vpn_wireguard_key` and `generate_vpn_wireguard_key`), `vpn:<id>:tlsKey`, `vpn:<id>:presharedKey` (WireGuard) and `vpn:<id>:password` (also written by import, from the profile's `auth-user-pass`). A `SecretSlot` with `oneTime` (VPN codes) is never read from the vault and never offered for saving. Connection slots are declared by the driver (`password`, `sshPassword`, `sshKeyPassphrase`). A `SecretSlot` with `store` belongs to another owner, so `withConnectPrompts` saves it with `set_owner_secret`. Vault keys are `key:<id>:private` and only generate and import write them.
- The UI only sees which slots are stored (`get_stored_secrets`, `list_saved_secrets`), except through `reveal_secret` (`vault/reveal.rs`). It returns one password, passphrase or token (`SecretOwner::revealable`, never `private` or `tlsKey`) after `confirm_user` passes. `copy_secret` writes to the clipboard from Rust and clears it after 30 seconds if it still holds the value. `export_key` and `export_vpn_profile` go through the same check.
- `unlock_secrets` runs `confirm_user` once and opens `RevealSession` for 5 minutes. While it's open, `reveal_secret`, `copy_secret` and `reveal_all_secrets` (every revealable value at once, never keys) don't ask again. `lock_secrets`, `lock_app` and a locked vault close it. Exports always ask.
- `confirm_user` asks the OS (`vault/os_auth/`), one prompt at a time: Windows Hello, else the Windows credential dialog checked with `LogonUserW` and the token's SID. macOS `LAContext` with `deviceOwnerAuthentication`. Linux polkit (`com.fran.app.reveal-secret`, `auth_self`, policy in `linux/`), registered once through `pkexec tee` when missing, else a GTK dialog in Rust checked through PAM (`polkit-1` service, else `login`). An account the OS says has no password passes without a prompt, unless the app lock is on, which then asks for its password. The no-password checks never count as failed logins: Windows tries a blank logon once per run, Linux asks `unix_chkpwd` directly instead of PAM.
- A missing required secret returns `secretsRequired`. `withConnectPrompts` (`src/helpers/connectFlow.ts` in the frontend) prompts, optionally saves to the vault, and retries. Use it for every connect-like call.
- If the keychain is unavailable the vault reports it. Never fall back to a weaker store.
- App lock (`vault/lock.rs`, Settings > Security): the vault key moves out of the keychain into `vault.lock`, wrapped (XChaCha20-Poly1305) with a key from Argon2id (64 MiB, 3 passes, random salt). The KDF settings are part of the AAD and bounds-checked before deriving. While locked, `Vault` holds nothing and every read returns `appLocked`. `lock_app` / `unlock_app` also seal and reopen the `DayLog`s. Sessions, terminals and forwards keep running. Agent approvals count only unlocked time toward their 5 minutes.
- Named secrets (`src/secrets/`) are values with a name, listed in `secrets.json` with the value in the vault as `secret:<id>:value` (`SecretOwner::Secret`). Items carry `secret_refs`, a map from a field path (`host`, `options.ssh.user`, `remotes.0.port`) or `slot:<name>` to a secret id. Each item type has `RefRules` for which fields and slots may use one, checked on save, and saves keep the text fields a secret fills empty (`fill::blanked`).
- `fill::Filler` fills those fields just before a connect, on the item's JSON by path. It's called where each item is read for connecting: `prepare_connect` (the filled profile is `Prepared.profile`), `RoutePlan::for_host`, `VpnPlan::for_profile`, the connection forward. A filled item never crosses IPC and is never saved, and `Filler::scrub` takes the values out of error text. A secret without a value leaves its field as saved and is noted, and `resolve_slots` asks for it in the same `secretsRequired` as the passwords, so every connect path must call it after its fills. A deleted one is an error. Connections fill only `live_refs`, so a secret left on a field the method skips (`DriverOptions::uses_field`) isn't read. Values with control characters are refused, since a field can end up in an OpenVPN config.
- `save_secret` with `copy_from` makes a secret from a saved password (revealable slots only, never keys) by copying it inside Rust, so the frontend never gets the value.
- A password slot that uses a secret is redirected with `Filler::redirect` (through `prepare::resolve_slots`, which every connect path uses instead of calling `resolve_secrets` itself): its `store` points at the secret, so the value is read from it and a typed one is saved to it.
- `DayLog` (`src/daylog.rs`) is one encrypted file per UTC day with its key in the vault, used by agent history and terminal logs. Sealed (app locked), appends wait in memory, up to 16 MiB, and are written on unlock.

## Cloud sync

- `src/sync/`. A cloud is one place items sync to, listed in `sync.json` (`state.rs`) with its cursor, each record's revision and the HMAC of what was last agreed (the HMAC key is `sync:local:hashKey` in the vault, so a password's hash can't be guessed from the file). Synced data names a cloud by its `identity` (instance id plus account id), never by its local id.
- `items.rs` turns every store and the vault into items keyed `<kind>:<id>` (`connection:<uuid>`, `vault:connection:<uuid>:password`, `setting:<key>`) and writes incoming ones back through the same stores. Settings sync per top-level key, without the ones that describe one computer (`LOCAL_SETTINGS`, `LOCAL_SETTING_PARTS`). Fran's own vault keys (`agent:`, `terminal:`, `cloud:`, `sync:`) never leave.
- List order is one item per list (`order:connections`, `order:sshHosts`, `order:vpn`), applied after the other items of a pull. The category defaults are the item `routes:categories` (`shared_routes.rs`, built from and applied to `sync.json` by the engine, never through `Stores`), with clouds by identity and `waitingRoutes` for one this computer lacks. For both, the cloud's copy wins when a computer first joins, and neither goes to "Replaced by sync".
- A setting both sides changed is merged per part against `RecordState.base`, the last agreed content, which is kept for settings only.
- `duplicates.rs`: after the first pull from a cloud, items no cloud has seen are matched to the cloud's by kind, name and target. They're held back from pushes until `settle_duplicates` merges them (passwords moved over, references rewritten to the kept id) or keeps both.
- `routes.rs`: an item's home is its own route, then its group's (`<kind>:<group>`), then its category's, else none. Passwords and keys can follow the item they belong to (`Target::WithItem`). An item that arrives from a cloud gets an item route to it. "Keep on this computer" stops both directions for that item.
- `engine.rs`: one worker per cloud. `JsonStore::watched()` stores and `Vault::modify` call `sync::notify::changed()`, which marks edits dirty at once (their time decides conflicts) and wakes the workers 2 seconds later. They also run every 5 minutes, on the provider's watch and on window focus. A pass pulls, applies, pushes with base revisions and goes again on conflict. The later edit wins, the other goes to "Replaced by sync" for 30 days (a password's old value in the vault as `sync:replaced:<id>`). Routes are read at push time, so nothing leaves through a stale queue. A move writes to the new cloud first, then tombstones the old one with `movedTo`.
- `providers/`: the `Provider` trait (`accepts`, `pull`, `push`, `watch`) and `opener`, the only match on `CloudKind`. `fran_server/` seals each item as one record (id is an HMAC of the item key under the data key, AAD is id and revision) and has sign-up, sign-in, recovery and the account calls. Its session token and data key are `cloud:<id>:session` and `cloud:<id>:dataKey` in the vault. `client.rs` uses https unless `http://` is typed out. Plain http is allowed to any host for testing, and the add form makes the user confirm a warning first.
- `providers/doppler/` holds secrets only, as normal Doppler secrets. A named secret with a `link` (the cloud's identity `doppler:<project>:<config>` and the name there) makes its value item (`vault:secret:<id>:value`) `pinned` to that cloud: `Homes` puts it there before any route, or nowhere when this computer doesn't have that cloud. The provider's `accepts` is false for every category, so nothing can be routed to it, and `takes` only lets pinned items through. Doppler has no revisions, so the provider keeps the last value it saw per secret in the vault (`cloud:<id>:seen:<secret id>`) with a counter that goes up when Doppler's value changes. Doppler's value always wins, the local edit goes to "Replaced by sync". A push sends `originalValue`, and a refusal is told apart from a conflict by reading the secret again, not by Doppler's error text. Only linked names are ever fetched, the token is `cloud:<id>:token`, and Fran never deletes in Doppler except through `doppler_delete_secret`. `Engine::refresh_linked` (after a failed connect) pulls the clouds that hold pinned items and says whether a value changed.
- Tests: `providers/doppler/tests.rs` runs the provider against a fake Doppler in the test process. `a_real_doppler_config_behaves_like_the_fake` needs `FRAN_E2E_DOPPLER_TOKEN` (write access) and makes and deletes one secret. `sync/tests.rs` runs two or three engines against an in-memory cloud. `fran_server/tests.rs` runs the provider against the real `fran-sync-server` binary (build it with `cargo build` in `server/`, or point `FRAN_SYNC_SERVER_BIN` at one), including a proxy that checks nothing readable reaches the server. Without the binary they print "skipped" and pass.

## VPN

- `vpn_store/` holds the profiles, `vpn/` the rest. `config.rs` reads an .ovpn (files it names only from its own folder) and writes the profile OpenVPN 3 gets, from the saved fields only, never with scripts, compression or the key. `keys.rs` reads client keys and signs Core's requests with `ring`.
- Own tunnels: `tunnel.rs` starts `fran-vpn --worker` (`crates/vpn-worker`, found next to Fran's exe by `vpn::sidecar`) and talks to it in `vpn-proto` frames over stdin and stdout, starting with a hello that carries `PROTOCOL_VERSION`. Only `vpn-worker` depends on `openvpn-rust-bindings` (from crates.io, with Core's source inside the crate), so only it compiles OpenVPN 3 and OpenSSL through the `cc` crate (needs a C++17 compiler and Perl for OpenSSL's build, which on Windows means Strawberry Perl). The worker runs `vpn_proto::profile::check` on every profile, which only takes what `config::core_profile` writes. `net.rs` is the smoltcp stack per tunnel, with DNS through the VPN's own servers (`dns.rs`).
- Fran's VPN service (`fran-vpn --service`, same binary): one tunnel per connection on `\\.\pipe\fran-vpn` (Windows, LocalSystem service `FranVpn`), `/run/fran-vpn/fran-vpn.sock` (Linux, systemd unit `fran-vpn`) or `/var/run/fran-vpn/fran-vpn.sock` (macOS, launch daemon `com.fran.vpn`), the same session code as own tunnels but with a real adapter (Wintun through `wintun.dll` loaded by full path, `/dev/net/tun` with rtnetlink, utun with `ifconfig` and `route`) instead of packets in frames. macOS uses a plain launch daemon in `/Library/LaunchDaemons`, not `SMAppService`, which needs signed releases. Its DNS goes into the dynamic store through `scutil`, its binary, `access` and `allowed` (user ids for "group" access, plus the `admin` group) live in `/Library/Application Support/Fran/vpn`, and "signed in at this computer" means owning `/dev/console`. `service/adapter.rs` works out the routes, bypass routes and DNS from `TunSettings` (Core's, or built from a WireGuard config) and the profile's `routeAll` and `useVpnDns`. DNS is `SetInterfaceDnsSettings` plus NRPT rules for split domains on Windows, systemd-resolved's D-Bus API on Linux. What it changes outside the adapter is written to `leftovers.json` first and undone on stop and on the next start. Callers are checked per connection (impersonation token or `SO_PEERCRED`): interactive and local sign-ins only, and with "group" access only administrators and members of `Fran VPN Users` / `fran-vpn`, read from the groups themselves. The setting is in `HKLM\SOFTWARE\Fran\Vpn` or the `access` file next to the installed binary. The app checks the other end too: the pipe must belong to the `FranVpn` service's process, registered to run `%ProgramFiles%\Fran\vpn\fran-vpn.exe` (both read from the service manager, since a non-elevated Fran can't open a SYSTEM process), the socket to root.
- `--install`, `--set-access` and `--uninstall` set it up, run elevated by `system/setup.rs` (ShellExecuteEx `runas`, `pkexec` on a copy in a private temp folder, or `osascript` with administrator privileges). Install copies the binary (and `wintun.dll`) to a folder only admins can write: `%ProgramFiles%\Fran\vpn` or `/usr/local/libexec/fran`. NixOS uses the flake's `programs.fran.vpnService` instead. `system/service.rs` (`ServiceVpn`) is the app's side, and `manager::ComputerVpn` holds it or `SystemVpn`. Both feed `system/adapter.rs` for connections bound to the adapter. A refused login or a CRV1 step becomes `VpnStatus.prompt`, answered on a fresh session.
- System mode (`vpn/system/`): the installed OpenVPN 2.6+ (`find_program`, on Windows the service's `exe_path` from the registry) gets `config::system_profile`, written to a fresh user-only temp folder that's removed on stop. `launch.rs` starts it through the Interactive Service pipe on Windows (needs an admin or "OpenVPN Administrators" member, `win.rs` checks with `reg query` and `whoami /groups`), `pkexec` on Linux and `osascript` with admin rights on macOS (output to a log file in the folder, since it runs in the background).
- Management runs with `--management-client`: OpenVPN connects to Fran, on a 127.0.0.1 port Fran already holds (Windows) or a Unix socket in the private folder (macOS, Linux). Fran checks the peer before saying anything: the connection's owning pid is the one the service reported (`GetExtendedTcpTable`), or the socket peer is root. There's no management password, and OpenVPN quits when the connection closes, so it never outlives Fran.
- `management.rs` parses the protocol. Logins go there (static challenges as SCRV1, dynamic ones as CRV1 with `--auth-retry interact`), and `>PK_SIGN` is signed with the vault key (`management-external-key pkcs1 pss digest`, so OpenVPN sends the message, not a hash). Something to type in mid-session (a new code, a refused password, a CRV1 step) becomes `VpnStatus.prompt` with its slots, and `answer_vpn_prompt` sends the answer back. The pushed DNS servers are read from the PUSH_REPLY log line.
- Connections through it bind to the VPN adapter found by its address (`if-addrs`, then `IP_UNICAST_IF`/`IPV6_UNICAST_IF`, `IP_BOUND_IF` or `SO_BINDTODEVICE`), IPv4 and IPv6, and fail instead of leaving another way. Names go to the pushed DNS servers over the adapter (`dns.rs`), else the computer's resolver. `SystemStream` errors as soon as the VPN goes down.
- `VpnProfile.system_options` holds the import's system-only options (name and plain-word arguments, or one quoted text for `cryptoapicert` and `pkcs11-id`) and is only set by import. The writer checks names and arguments again, since `vpn.json` can be edited by hand. `pkcs11_provider` is only ever set in the editor, never from a file. With either, OpenVPN signs itself and Fran has no key (`config::key_outside_fran`).
- A PKCS#12 file in a profile (`pkcs12` file beside it or inline) is opened on import with `p12-keystore`, after `secretsRequired` asks for its password (`config::PKCS12_SLOT`, one-time). Its key goes to the vault like a PEM key, its other certificates become the CA when the profile names none.
- `cargo test --features e2e --test e2e -- vpn::system_mode` with `FRAN_E2E_SYSTEM_VPN=1` runs system mode against the lab with the installed OpenVPN. In the `fran-linux-check` image it runs as root (Fran starts OpenVPN itself instead of through pkexec) with `--cap-add NET_ADMIN --device /dev/net/tun`, Docker's socket mounted and `OVPN_LAB_HOST` set to the WSL address.
- WireGuard: `VpnProfile.kind` is `openVpn` (also for profiles saved before it existed) or `wireGuard`, whose fields are in `wire_guard` with the endpoint as `remotes[0]`. A profile never switches kind. `vpn/wireguard.rs` reads wg-quick files (one peer only, `PreUp`/`PostUp`/`PreDown`/`PostDown` dropped, names in `DNS` become search domains), checks the editor's fields and builds `WireGuardStart`. The worker runs it with boringtun in `crates/vpn-worker/src/wireguard.rs`, through the same `Tun` as OpenVPN: up means the first handshake finished, AllowedIPs become `TunSettings` routes (`/0` sets the redirect, the endpoint is kept outside), and decrypted packets from outside AllowedIPs are dropped. Unlike OpenVPN keys, the private key goes to the worker or service with `StartWireGuard`, since WireGuard has nothing to sign with. It's only kept in memory there.
- Turning a VPN on for the computer goes through Fran's service for WireGuard always, and for OpenVPN unless `settings.vpn.systemWith` is `openvpn` or the profile needs the installed OpenVPN. A service that isn't set up is an error (the frontend offers to set it up first), never a quiet switch to the installed OpenVPN.
- `manager.rs`: per profile an own tunnel and a system VPN. A lease asks which is current on every connect, so switching only moves new connections. While the system VPN is on (also while it reconnects) connects wait for it and never open an own tunnel. Own tunnels close after `settings.vpn.idleCloseSecs` (passed in with `set_vpn_options`) once the last lease is gone. It's installed once as a global so routes and drivers reach it. SSH hop 1 goes through `SshRoute::vpn`, direct MySQL and Postgres connections through `VpnRelay`. Generic code asks `DriverOptions::network_target`.

## Tray

- `tray.rs`: closing the main window hides it while `settings.keepInTray` is on (passed in with `set_tray_options`) and a tray exists. Otherwise, and for Quit in the tray menu, Rust emits `quit-requested` and the window confirms what stops before calling `quit_app`. Until the window has sent its settings, closing just closes.
- The menu is built from items the frontend sends (`set_tray_menu`), since it knows what's running. Clicks that need the window emit events (`tray-vpn`, `tray-forward-stop`, `tray-lock`). The icon gets a green dot while a VPN is on for the computer. Linux needs libayatana-appindicator at runtime (the flake puts it on the library path).

## Files

All in the Tauri app data dir: `connections.json` (profiles, no secrets), `known_hosts.json`, `ssh.json` (SSH hosts, identities, key metadata, proxies, forward rules, host group order), `vpn.json` (VPN profiles with public certificates, no keys), `secrets.json` (named secrets, no values), `sync.json` (clouds, routes, record revisions, no secrets), `snippets.json`, `saved_queries.json`, `tab_state.json`, `settings.json`, `secrets.vault`, `vault.lock` (only with the app lock on), `agent.json`, `agent_history/`, `terminal_logs/`.

`settings.json` and `tab_state.json` are owned by the frontend, Rust only stores the JSON. `JsonStore` refuses to overwrite a file it failed to parse.
